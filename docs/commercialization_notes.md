# 商用化・20文字チャットに関する方針メモ

2026-06-12 時点の検討内容の記録。法的事項は一般的な制度の整理であり、
課金開始などの節目では専門家または当局（総合通信局・無料）に確認すること。

## 1. OSS と商用運用の方針

### 現状
- リポジトリは **MIT ライセンス**で公開済み（https://github.com/me-keh-dev/1f）
- 一度 MIT で公開した版は取り消せない。非公開化しても既存の clone/fork は
  その版を永久に MIT の権利で使える。変えられるのは「今後の版」だけ
- bootstrap 方式で素の .py を配布しているため、クライアント側の課金チェックは
  技術的に保護できない（クライアントは全部見える前提で設計する）

### 決定方針: 「OSS 継続 ＋ サーバ側で課金」
- LINE スタンプ型（コードは公開、収益はコンテンツとサービス）
  - 前例: Aseprite / Mindustry / VS Code など
- 1/f での「スタンプ」に相当するもの:
  - プレミアムシーン・スプライトパック（**サーバから配信**し、リポジトリに入れない）
  - ポイントはサーバ側で管理（既存の Cloudflare D1 ＋ 匿名 uid 基盤が土台）
- **線引きルール（今から守る）**: 課金対象にしたいアセットは最初から
  リポジトリに入れない。「エンジン = MIT、有料コンテンツ = プロプライエタリで
  サーバ配信」
- チャットの**サーバ側コードは非公開**にする。クライアントが MIT でも、
  価値はネットワーク効果（ユーザーがいる場所）にあるため競合は成立しない
- 代替案（不採用だが記録）: 今後の版のみ PolyForm Noncommercial / BUSL 等の
  「ソース公開・商用不可」ライセンスに切替える中間案もある

## 2. 電気通信事業法（日本）— 20文字チャットの届出

### 該当性の判定（総務省フローチャート）
1. 電気通信回線設備を設置するか？ → **設置しない**（Cloudflare 等の借用）
2. 他人の通信を媒介するか？ → チャットの形態で分かれる:

| 形態 | 判定 |
|---|---|
| 1対1のDM・招待制グループ（特定の相手に届ける） | **媒介に該当 → 届出が必要** |
| 全員に公開のオープンなつぶやき・掲示板型 | 媒介に非該当 → 届出不要の可能性が高い |

- 「媒介」= 他人の通信を内容を変えずに特定の受信者へ届けること（LINE が届出事業者なのは同じ理由）
- 問い合わせフォーム（訪問者→運営者）は自分宛て通信なので媒介ではない

### 「事業」要件（営利性）
- 届出対象は「事業として営む」= 営利目的・反復継続の場合
- **完全に無収益**（課金なし・広告なし・投げ銭なし・他の有料サービスへの誘導でもない）
  の個人運営は「事業」に当たらず届出不要、というのが一般的な整理
- 「収益」は広く解される: ユーザー課金 / 広告収入 / 継続的な投げ銭・寄付 / 間接収益

### 届出の実務
- **猶予期限はない**。「事業開始前に、あらかじめ」届出（電気通信事業法16条）。
  無届出営業には罰則あり（6月以下の懲役または50万円以下の罰金）
- **手数料: 無料**（「登録」は登録免許税15万円だが、自前で回線設備を持たない限り不要）
- **資格: 不要**（試験・免許なし。個人でも届出可能）
- 提出先: 管轄の総合通信局（書類1回）
- 届出後の義務: 通信の秘密の保護 / 提供条件の説明・苦情対応 / 廃止・変更時の届出
- 届出不要でも適用される規律あり: 通信の秘密（届出の有無に関係なく適用）、
  外部送信規律（2023年施行、日本版Cookie規制）など

### 決定スケジュール
| フェーズ | 対応 |
|---|---|
| 無料・無広告でチャットをリリース | 届出不要で整理が立つ。通信の秘密を守る設計に |
| ポイント課金・広告など収益化を開始 | **その前に届出**（無料・書類1回・資格不要） |

- 段階案: まず「全員に見えるオープンな20文字つぶやき」で開始（届出なし）→
  DM 機能を足す段階・収益化の段階で届出、という進め方も可能

## 3. 海外ユーザー（シンガポール等）

- **日本の届出義務は変わらない**（事業を営む場所 = 日本 基準）。
  海外ユーザーがいても「収益化前に届出」のままで OK
- 各国の通信ライセンスは回線・通信網を持つ事業者向けで、OTT チャットアプリ
  （WhatsApp / LINE 型）にライセンスを課す国はほとんどない。シンガポール（IMDA）も不要
- 現実的に効くのは**プライバシー法**:
  - シンガポール: PDPA / EU ユーザーがつけば: GDPR（域外適用あり、最も重い）
  - **プライバシー法は無料サービスにも適用される**（「収益化したら」ではない）

## 4. チャットリリース時の最小コンプライアンス対応

- 収集データを最小に設計する（匿名ID ＋ 20文字本文のみ、など）。
  データ最小化そのものが最良の GDPR/PDPA 対策
- プライバシーポリシーを**日英**で用意し、収集内容・保存期間・削除方法を明記
- 通信の秘密を守る設計（メッセージ内容を正当な理由なく見ない・漏らさない）
- 通報・モデレーションの仕組み（ユーザー生成コンテンツを預かるため）

## 5. liplico との分離構成（メールソフト型）

20文字通信は別サービス **liplico**（自社運営・アカウント/ログインを持つ・
**商標登録出願済み**）として運営し、1/f はその**クライアント（窓口）**になる。
Gmail に対するメールソフトの関係。

- **1/f（クライアント）**: ただのソフトウェア。メールソフトが電気通信事業者で
  ないのと同じで、**1/f 自体に届出等の規制はかからない**。MIT・OSS のまま
- **liplico（サービス）**: 通信を媒介する側。届出義務・通信の秘密・プラポリ・
  利用規約・課金は**すべて liplico 側に集約**（自社運営なので義務は消えず
  liplico に紐づくだけ）
- 1/f は liplico にログインしなくても従来通りのアンビエントアプリとして完結。
  チャットはオプトインの窓口機能
- liplico の規約・プラポリ・届出を1セット整備すれば、将来の別クライアント
  （スマホアプリ等）にも流用できる
- アカウント基盤は分離: 1/f の匿名 uid（統計用）と liplico アカウント（ログイン）
  を混ぜない設計にする

## 6. OSSクローン対策 — Thunderbird 方式（コードは守らず、ブランドと場を守る）

懸念: シーンマーケット（ユーザーがシーンを作って販売）を始めた場合、OSS だと
同じサービスを即時立上げされうる。Thunderbird/Mozilla の実例に倣う。

### Thunderbird の実際
- コードは MPL 2.0 で完全公開。フォークも実在（Betterbird 等）し、防いでいない
- 守っているのは**商標**。名前とロゴは登録商標でフォークは改名を強制される
  （Debian の Iceweasel 事件）→ 認知・信頼・検索流入は持っていけない
- 収益はコードの外（Thunderbird は寄付、Firefox は検索契約）

### 1/f への当てはめ — フォークで奪えないもの
| 資産 | フォークで奪えるか |
|---|---|
| クライアントのコード | 奪える（MIT） |
| ブランド名・ロゴ | 商標登録で奪えない（**liplico は出願済み**） |
| シーンマーケット（サーバ・決済・クリエイター報酬） | リポジトリに入れなければ奪えない。フォークは「ストアが空の再生機」 |
| クリエイターと購入者のネットワーク | 奪えない。二面市場＝最大の堀（LINE スタンプと同じ） |

- 類例: Android。AOSP は完全 OSS だが Google Play（マーケット）が非公開で実質の独占力
- 任意の追加防御: 今後の版を MPL 2.0 に切替えると「フォークを非公開で商用化」
  しにくくなる（MIT より一段防御的、OSS のまま）

### シーンマーケット構想
- ユーザーが自分でシーンを作成・追加・**販売**できるようにする予定
- マーケットのサーバ側・決済・有料シーンデータはリポジトリに入れない

### モードの線引きルール（決定方針）
| 対象 | 扱い |
|---|---|
| エンジン（main.py・scenes/base.py・更新/統計基盤） | OSS 継続 |
| 既存7モード＋今後の**無料**モード | OSS 継続（アプリの顔＝store への集客装置。クリエイター向けの教材にもなる） |
| 今後の**有料**モード（自作・ユーザー作問わず） | リポジトリに入れない。liplico store から配信 |

- 運用: 新モードを作るたびに「無料（→リポジトリへ）か有料（→store 配信・リポジトリ外）か」を決めるだけ
- 配信フロー: 無料の新モードは既存の自動更新（起動時に code.zip を確認→DL）で
  全ユーザーに自動配布。有料モードは購入後に liplico store から個別 DL
- scenes/base.py の OSS 公開はマーケットの前提条件（シーン API とサンプル実装が
  公開されていないとユーザーがシーンを作れない）
- 有料モードも .py としてクライアントに届くためコピーは技術的に防げない（LINE
  スタンプと同じ）。DRM ではなく「正規に買う方が楽・安い・作者に還元される」
  体験と store という場に投資する

## 7. アーキテクチャの見通し

- 既存基盤の延長で実装可能: Cloudflare Pages + D1 ＋ Durable Objects + WebSocket（小規模チャットの定番構成）
- 20文字制限は DB・帯域・モデレーションの全コストを下げる設計上の利点
- ポイント課金もサーバ側 uid 基盤（stats_uid）がそのまま土台になる

## まとめ（行動指針）

1. OSS は継続（MIT）。有料アセット・チャットサーバ側コードはリポジトリに入れない
2. 20文字チャットは無料・無広告でリリース → 届出不要
3. 収益化（ポイント課金・広告）の**前に**電気通信事業の届出（無料・資格不要）
4. プライバシーポリシー（日英）とデータ最小化は**最初から**整備
